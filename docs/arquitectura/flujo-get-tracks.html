Flujo Vertical Slice — GET /api/library/tracks

Propuesta para validar: archivos, clases y métodos implicados cuando la página Tracks obtiene un listado (años, estilos o canciones). Inspirada en Anton Martyniuk (Endpoint + Handler + Validator por slice), simplificada: sin MediatR, sin reflexión para endpoints/handlers, sin eventos ni módulos. Validación de formato con FluentValidation aplicada automáticamente a toda la API; errores de negocio con FluentResults; middleware solo para lo imprevisto.

1. Reglas de la arquitectura

  • UI: el code-behind de cada página hace la petición HTTP con el HttpClient de la API, usando las extensiones compartidas GetForResultAsync/PutForResultAsync, que devuelven Result<T>. Sin API clients intermedios.
  • Endpoint: define la ruta, recibe el request, llama al handler y traduce el Result a HTTP. Una línea de cuerpo. Sin validación, lógica ni try/catch.
  • Validación de formato: reglas FluentValidation en <Feature>Validators.cs (un archivo por feature). Las ejecuta un único filtro aplicado al grupo /api: ningún endpoint puede olvidarlo. Todo parámetro *Request debe tener validador o la API falla al construir el endpoint.
  • Handler: recibe el request ya validado. Reglas de negocio (ajustes, disco), orquesta Infrastructure, logs y devuelve Result<T>. Crea sus errores en el punto donde ocurren (sin clases <Feature>Errors).
  • Infrastructure: ficheros, tags y ajustes. Devuelve Result para fallos esperables (carpeta inexistente, JSON de ajustes inválido o inaccesible). Las demás excepciones se propagan.
  • Errores: una sola clase AppError con un ErrorKind, compartida por Api, Infrastructure y UI. Un único switch traduce ErrorKind → código HTTP; la UI no hace la traducción inversa.
  • Imprevistos: el manejador integrado de .NET (AddProblemDetails + UseExceptionHandler) registra la excepción y responde 500 ProblemDetails. Sin clase propia.
  • Registro explícito: cada feature expone los métodos de extensión Add<Feature>Feature() (registra directamente sus handlers) y Map<Feature>Feature() (mapea directamente sus endpoints). Navegable con «Ir a definición». Solo los validadores se registran por escaneo (una línea).

Filtro de validación del grupo /api

Archivosrc/DjTracks.Api/Shared/ValidationFilter.cs (nuevo, único para toda la API) Métodostatic EndpointFilterDelegate Create(EndpointFilterFactoryContext context, EndpointFilterDelegate next)
Se ejecuta una vez al construir cada endpoint:
  1. Recorre los parámetros del Handle (context.MethodInfo) cuyo tipo termina en Request.
  2. Resuelve su IValidator<T>. Si no existe → InvalidOperationException("GetTracksRequest no tiene validador"): la API no atiende ese endpoint sin validar.
  3. Si el endpoint no tiene request (p. ej. GET /api/settings) devuelve next sin coste.
En cada petición: 
foreach (var (index, validator) in validators)
{
    var validation = await validator.ValidateAsync(
        new ValidationContext<object>(ctx.Arguments[index]!), ctx.HttpContext.RequestAborted);
    if (!validation.IsValid)
        return Results.ValidationProblem(validation.ToDictionary(),
            validation.Errors[0].ErrorMessage, title: "Revisa los datos enviados.");
}
return await next(ctx);
Inválido → 400 con errores por campo; endpoint y handler no se ejecutan.

Handler: lógica del caso de uso

Archivosrc/DjTracks.Api/Features/Library/GetTracks/GetTracks.Handler.cs (nuevo) ClaseGetTracksHandler(JsonSettingsStore settings, TrackLibrary library, ILogger<GetTracksHandler> logger) MétodoTask<Result<TrackListing>> HandleAsync(GetTracksRequest request, CancellationToken ct)
Secuencia (el request ya llega validado): 
var settings = await settingsStore.LoadAsync(ct);
if (settings.IsFailed)
    return settings.ToResult();   // error ya creado y registrado en JsonSettingsStore
if (string.IsNullOrWhiteSpace(settings.Value.Tracks))
    return new AppError(ErrorKind.Conflict, "Configura la ruta de Tracks.",
        "Abre Configuración y guarda las rutas antes de explorar la biblioteca.");
try
{
    var listing = library.Browse(settings.Value.Tracks, request.Year, request.Style, ct);
    // LogWarning por cada pista con Warning (tags ilegibles)
    return listing;
}
catch (Exception ex) when (ex is IOException or UnauthorizedAccessException or NotSupportedException)
{
    logger.LogError(ex, "No se pudo explorar la biblioteca de Tracks");

Lectura de ajustes (devuelve Result)

Archivosrc/DjTracks.Infrastructure/Settings/JsonSettingsStore.cs (modificado) MétodoTask<Result<PathSettings>> LoadAsync(CancellationToken ct) (antes Task<PathSettings>)
Traduce una sola vez los fallos del fichero de ajustes para todos los handlers que lo leen (Tracks, Settings y, más adelante, Sessions, Remember y Playlists):
  • JsonException → AppError(Unexpected) «El JSON de ajustes es inválido. Corrígelo o restaura una copia en el servidor y vuelve a cargar.»
  • IOException/UnauthorizedAccessException → AppError(Unavailable) «Comprueba los permisos y la disponibilidad del fichero de ajustes en el servidor.»
Recibe ILogger<JsonSettingsStore> y registra la excepción con LogError en el mismo catch; los handlers solo devuelven el error. SaveAsync devuelve Task<Result> con el mismo criterio (mensajes «No se ha sobrescrito» / «No se ha confirmado ningún guardado»).

Result → respuesta HTTP

Archivosrc/DjTracks.Api/Shared/ResultExtensions.cs (nuevo) MétodoIResult ToHttpResult<T>(this Result<T> result)
if (result.IsSuccess) return Results.Ok(result.Value);
var error = result.Errors.OfType<AppError>().First();
var status = error.Kind switch
{
    ErrorKind.Validation  => 400, ErrorKind.NotFound    => 404,
    ErrorKind.Conflict    => 409, ErrorKind.Unavailable => 503,
    _                     => 500
};
return error.FieldErrors.Count > 0
    ? Results.ValidationProblem(error.FieldErrors, error.Message, title: error.Title, statusCode: status)
    : Results.Problem(error.Message, title: error.Title, statusCode: status);
